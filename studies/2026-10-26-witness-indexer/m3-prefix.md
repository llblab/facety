## Phase 1: bounded FIFO simple-prefix frontier

Start from `[U]`; it consumes one lifetime-enqueued-prefix slot. A zero maxPrefixes records prefix-limit truncation and admits no prefix. Keep FIFO order with indexed head and a total-enqueued limit, not a refillable live queue cap. Each queued prefix is a simple path in the current subject-first graph projection. **Do not globally mark a vertex visited:** different simple prefixes ending at the same vertex can have different usable tree tails and family conflicts. The per-prefix visited set prevents cycles, not alternate routes. Prefixes never exceed maxPrefixHops or the policy hop bound.

At an expanded prefix ending at V, optional intermediary eligibility applies before extending V: U is exempt; any other V needs its current qualifying score when minStanding is enabled. Low/unknown score V may still terminate a valid path but may not extend as an intermediary. An anchor may be transit if ordinary score/edge policy allows it; authorized removal disqualifies it as a terminal, not automatically as every transit vertex. Do not add blanket terminal-only or score-off checks.

If prefix depth already equals the policy hop limit, no extension is needed. Otherwise enumerate V's current projected neighbors in capture order. Each neighbor visited by this scan consumes one maxExpansions trial, including already-used vertices; exact-last-budget exhaustion is not censoring unless another trial is actually needed. If the neighbor budget prevents completing a scan, record expansion-limit and stop frontier expansion, retaining all prefixes already queued. Do not treat an unexamined neighbor as absent.

Remove vertices already in this prefix. If maxPrefixHops is smaller than the policy hop bound and prevents a possible extension, record prefix-depth-limit and continue other queued prefixes. If no extension is possible, no pool is required. If extension is possible but V has no supplied pool row, record pool-unavailable and continue other queued prefixes. A missing row is not empty adjacency.

For a supplied row, exclude retained peers that are not current unused neighbors, without refilling below top-M. Track full eligible-neighbor versus retained-peer omission counts separately; intentional top-M/unknown-score omissions do not make the graph complete. Sample at most maxBranches retained eligible peers without replacement under the key contract below, keeping loads unchanged. If eligible retained peers remain unchosen, record branch-limit but still explore selected peers. Append each selected peer to its own copied prefix. If another enqueue is needed after maxPrefixes is reached, record prefix-limit and stop frontier expansion; retain all already queued prefixes, including unexpanded ones. Every queued prefix has already passed edge/simple checks and may participate in phase2. MaxPrefixes is not a count of distinct vertices, grants or successful admissions.

Telemetry distinguishes queued/expanded prefixes, maximum pending frontier, raw neighbor trials, score reads, actual route calls/draws, sampled peers versus actually enqueued prefixes, missing-pool occurrences and intentional omissions. Per-prefix route summaries may retain prefix/pool/query-key IDs, selected peers and work counts, not repeated full pool snapshots. Normalized pool/load inputs are retained once. State is bounded by explicit prefix/path/pool limits; preparation, hashes/UTF-8/JSON, neighbor scans, snapshots, route/result allocation and search costs remain separate.

## Phase 2: current direct-prefix/tree joins and final assembly

Traverse all admitted prefixes in FIFO admission order, even those not expanded before a limit. At each prefix: first emit the positive-length prefix itself if its endpoint is currently an eligible nonremoved snapshot anchor; then retrieve its endpoint's tail toward each retained forest anchor in forest order. Join by replacing the shared endpoint once: `prefix.slice(0,-1) + tail`. A zero-hop tail can close a positive prefix, but zero-hop U→U alone never counts. Charge every attempted tail lookup, including null/zero-hop, to maxTreeLookups. When lookup budget blocks another retrieval, record tree-lookup-limit and skip further tail retrievals while still permitting direct-prefix candidates; do not stop phase1 or invent unavailable tails. A stale tree can contribute only currently valid paths.

Every emitted positive-length candidate consumes maxCandidates before final hop/simple/current-policy rejection or exact-array deduplication. A tail may repeat an earlier prefix vertex or exceed r; full-path checks must reject it before packing/encoding rather than trusting the valid prefix or valid tail independently. Then use existing bounded exact D-packing and both M1 verifiers. Endpoint/transit conflicts and distinct terminals count exactly as before. Packing is exact only over retained validated candidates and remains exponentially bounded by maxPackingSteps; do not claim an ordinary or layered-flow solution.

Keep the existing `facety-path-proposal/v1` result envelope, adding a deeply frozen `prefix` record with reference `bounded-prefix-tree/v1`, the composite randomness descriptor, normalized advice, admitted-prefix and route-summary arrays, work stats and coverage flags. Other proposal fields retain their current meaning. Before availability is established, coverage is null (not complete) and frontier/draw/lookup work is zero. Configuration errors throw. Forest/view/policy/epoch availability rules remain explicit; unavailable returns follow data preflight and do no frontier draws/edge trials. Found requires a canonical wire accepted by both verifiers and may occur despite any search/forest truncation. All other results have feasible:null and no witness. For a negative, report all coverage flags and choose reason priority: packing-limit, candidate-limit, prefix-limit, expansion-limit, branch-limit, prefix-depth-limit, pool-unavailable, tree-lookup-limit, tree-build-incomplete, then miss. A fully traversed retained frontier with no limit still yields miss, never global infeasibility: table omissions, top-M pruning and one-parent tails are not completeness certificates. A separately budgeted full M2 fallback remains outside this helper. No implicit new recovery work or load update is authorized.
