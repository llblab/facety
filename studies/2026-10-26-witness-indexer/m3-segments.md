## Chosen owner, scope and API

Use a new cohesive `src/path-witness-segments.mjs` owner for `PathWitnessSegmentCache` and `PATH_SEGMENT_LIMITS`. It owns bounded partial-path retention, current local checks, relation-reference continuity, logical TTL/use bookkeeping and conservative eviction. It does not import trees/pools/search/Model or become a generic cache utility. It may depend on the existing context/policy and immutable-view public contracts plus Node crypto. Whole-witness PathWitnessCache continues to own dual-verified certificates and exact fallback; prefix/tree assembly continues to own full path/family verification. No existing API/default/source behavior changes in this contract checkpoint.

A retained segment is a positive simple subject-first path `[from,...,to]` within the supplied policy hop/ID limits. It is **not a witness**, unique-person proof, terminal-anchor assertion, guarantee/duty record or authorization to burn/admit. Source/sink endpoints are locally score-exempt; internal vertices obey minStanding only when enabled. An endpoint may become an intermediary after splicing, so its score must then be checked. Anchor membership/removal and difficulty are not local segment roles. A removed anchor can still be a permitted unshared transit vertex; no generic vertex exclusion is invented from removal.

Future API:

- Constructor: exact `{ledgerId,maxEntries,maxBytes,ttlTicks}`; nonempty bounded opaque ledgerId declares an operator-supplied graph-lineage namespace, not authentication.
- `put(view,context,{epoch,path,tick})`: normalize/copy bounded data, check the current local path and collect actual stored edge references, then retain/explicitly refresh or return rejected/unavailable/not-stored. Context subject must equal path[0].
- `lookup(view,context,{epoch,to,tick,maxChecks,maxResults})`: inspect the matching endpoint bucket in FIFO order, recheck current local policy and recorded relation identities, evict failures and return bounded alternatives. Context subject is from. There is no wildcard/global search or implicit fallback.
- `invalidate({edges,vertices})`: bounded untrusted stored-edge-pair/vertex notices evict advisory records only. No canonical state, guilt, score or emergency flag is changed.
- `stats()`: frozen inert inventory/clock/index/usage snapshot, no expiry sweep, time advance, revalidation, use increment or RNG.

All records/arrays use exact plain data, no accessors/coercions/callbacks, well-formed Unicode and raw bounds before dedup/filtering. Supported dense arrays are standard/null-prototype, not exotic subclasses. A copied view is refused; a locally constructed view is still not authenticated state. Complete policy ID must match the capture. Epoch must exist and be within the policy's current grace range. Missing/non-live vertices or dead/score-invalid paths are local rejection, not personhood verdicts. No extra Standing=XP derivation is selected.

## Identity and projection continuity

Scope keys include ledgerId, context domain, capture reference, storage graph name, full policy ID, epoch and endpoints. Those labels do not establish a real ledger or independent operator; same-ledger capture lineage is a declared caller assumption. Graph names and tokens such as edge:0 are not globally unique. Do not mix unrelated ledgers under the same namespace or advertise identity continuity outside that assumption.

For every subject-first hop `[x,y]`, collect live stored orientation/id references from `view.toJSON().source.storage.edges`, checked against `view.edge`. Directed-from-anchor requires the stored y→x edge. Reciprocal-only requires both stored orientations. Any-live-orientation records **all currently live orientations**, not an arbitrarily selected reciprocal rule. References are bounded and sorted by unsigned UTF-8 from/to/id; identity is a local freshness/custody diagnostic, not a new protocol guarantee meaning.

On reuse, directed/reciprocal hops require the corresponding original orientation IDs still live. Any-live hops require at least one originally recorded orientation ID still live. A newly appeared alternative orientation cannot silently rebind an old segment if none of its original references survives. Removal/re-add creates a new relation reference and causes an old-segment miss/eviction even when the same vertex-only witness now passes M1/ref2. Explicit put revalidates and may store a new segment ID. **Never migrate this stricter reuse rule into M1 witness acceptance.**

A changed capture root alone does not invalidate a segment whose original relations and current local predicates still hold; unrelated appends may change the root. Matching roots/IDs alone never bypass current checks. Old immutable captures remain old, so the caller must supply the intended coherent current capture; this cache adds no authentication, finality, reorg, atomic authorization or canonical-clock service.

Use segment ID = lowercase SHA256 of UTF-8 JSON array `['facety-path-segment/v1',ledgerId,domain,reference,graphName,policyId,epoch,path,hopReferences]`. Each hop reference list uses exact `{from,to,id}` records in the stated order. Store multiple alternatives per endpoint pair, including different paths or incarnations, but deduplicate identical IDs. The immutable payload for byte accounting is this exact JSON array, not a full witness wire or signature. ID/content hashes do not authenticate the supplier or historical duty.

## Storage, logical clocks and usage

Software maxima:1024 entries,1048576 immutable payload bytes,1000000 TTL ticks,1024 checked entries and64 returned segments per lookup,4096 raw edge notices and4096 raw vertex notices. Paths use the witness policy's r<=64/ID<=256-byte bounds; ledgerId<=256 UTF-8 bytes and stored edge-ID tokens<=64 bytes. Oversized/unsupported identity metadata makes retention unavailable rather than invalidating the graph. Zero entry/byte capacity disables retention, not local validation. TTL must be positive. These are engineering limits, not protocol quotas, calibrated human rates or memory/CPU benchmarks.

Insertion/replacement is FIFO; identical-ID put is an explicit fresh verification/retention cycle, moves it to the FIFO tail, resets its within-cycle use count and sets origin/last-verified root and verification tick. A new incarnation has a different ID. Evict oldest entries until both limits hold; a single payload above maxBytes is not retained. Every removal/refresh cleans endpoint, edge and vertex reverse indexes. Payload bytes exclude bookkeeping/maps/index multiplicity and mutable counters: report those inventory counts separately and do not call maxBytes a total-process memory bound.

Ticks are caller-supplied monotonic nonnegative safe integers, separate from view epoch/Model hour/wall time. Expire at `tick>=expiresAt`, with `expiresAt=storedAt+ttlTicks`; no hit-based TTL renewal, clock refill or automatic epoch rebinding. Put must reject expiry overflow before mutation; lookup may use any safe tick, including a final sweep tick. Data/clock validation errors throw before entry/index/clock mutation. Well-formed put/lookup advances the logical clock and sweeps expiry even when the requested epoch/path is unavailable; these are cache effects, never protocol-state transitions. Invalidate and stats do not advance time. TTL staggering/jitter remains deferred; this first profile uses deterministic fixed logical TTL, not hidden RNG.

Each segment actually returned by lookup increments its within-cycle `uses` once and updates verifiedAt/lastVerifiedRoot, without changing storedAt/expiresAt/FIFO order. Validation of an entry not returned earns no use. Repeating lookup is another advisory return event; it is not idempotent human work or a protocol action. stats is inert. Uses saturate at Number.MAX_SAFE_INTEGER; the next attempted increment sets usesSaturated:true rather than rounding/overflowing. Saturated values mean at least that count. Do not sum capped uses as exact lifetime work or use hotness as evidence/truth/XP. Hot here means reusable/observed; no usage-ranked eviction or future workload policy is silently selected.

## Lookup results and benign invalidation

Malformed host data throws. Well-formed semantic failure/unavailable state yields explicit reasons with no partial acceptance claim. put statuses are stored/not-stored/rejected/unavailable; local rejection covers zero-hop/non-simple/dead-edge/current-score/vertex failures. A zero-length raw path is malformed. No operation/result exposes accepted, feasible, witness or a certificate wire; successful local checking cannot discharge M1/ref2 or D41.

Lookup has hit if results exist and the bucket scan is complete, partial if results exist with unexamined bucket entries, miss if none exist after complete cache scan, censored if none exist with unexamined bucket entries, and unavailable for the epoch/capture precondition. Report completeCacheScan and result/check-limit reasons explicitly. Complete means this endpoint bucket only, never public graph completeness/no-path. maxChecks/maxResults may be zero; equality with a limit is not censoring unless another matching record remains. Count expired/evicted/checked/returned/local predicate/id checks and any storage-index preparation separately. Do not fabricate a graph-negative result from disabled retention, absent entries, poisoned metadata, TTL or budget.

Retain originRoot/storedAt/expiresAt and report currentRoot/lastVerifiedRoot/verifiedAt separately. Current edges, internal scores and original references are rechecked on **every** returned segment, even at a matching root. A cache miss can coexist with a valid current full witness; a cache hit can coexist with an invalid spliced/full witness due to endpoint roles, cycles, hop limits, terminal eligibility or cross-path conflicts.

Edge notices are actual stored guarantee orientations, but conservatively evict both orientation indexes; vertex notices evict every segment containing that vertex, not only its terminal. False/overbroad notices can cause extra misses/work, not canonical removal. Thus an anchor-removal notice may harmlessly evict a segment that could legally transit that vertex; missing notices are still caught by current checks when relevant. Generic segments do not interpret a vertex notice as an independent violation or a verdict.

## Validation and next boundary

Before source exists, use the current capture and both M1 verifiers to retain these analytic controls: unrelated-root change with the same live stored ID; remove/re-add with changed ID but still-valid vertex witness; any-live opposite-orientation replacement versus surviving recorded orientation; reciprocal loss rejecting a full witness; a removed endpoint failing as terminal but remaining usable as transit; and an endpoint-score exemption that disappears when it becomes intermediate. These checks explain the selected cache role/identity contract, **not implementation acceptance**.

Future implementation tests need an independently written raw path/reference checker plus primary/ref2/full-M2 stitching controls, exact TTL/endpoints/expiry overflow, refresh/FIFO/byte/disabled capacity, multiple alternatives/check-result limits, all index cleanup paths, duplicate/raw/Unicode/malformed inputs, inert stats/use/clock semantics, stale current predicates and relation reincarnation, no implicit anchor roles/RNG/fallback/Model mutation. Any memoized immutable-view map is not a canonical cache. No O(k*r) whole-operation, scaling or speed claim follows.
